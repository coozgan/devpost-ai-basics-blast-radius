# Blast Radius

Paste a `terraform plan -json` and see what the change can actually reach — before versus after.

A Terraform plan tells you *what changes*. It never tells you *what that change can now touch*.
Blast Radius computes reach from the plan's own data on both sides of the diff, so a five-line
policy addition that triples what a role can reach reads as a five-line diff in review — and as
`reachable paths 1 → 6` here.

Built for the Devpost [Build With AI: Basics](https://learn-ai-basics.devpost.com/) hackathon
using the Devpost Learn Skill Pack. The plan that produced it is in [`devpost/`](devpost/):
[scope](devpost/scope.md), [PRD](devpost/prd.md), [spec](devpost/spec.md),
[build checklist](devpost/checklist.md).

## Run it

```sh
python3 -m http.server 8000     # ES modules are blocked on file://
# open http://localhost:8000 and click "Load the example plan"
```

```sh
node --test                     # 10 assertions over the committed example plan
```

No dependencies, no build step, no server-side processing, no network calls after page load.
The pasted plan never leaves the browser.

## What it computes

Four edge kinds, all derived from a single `terraform show -json` document:

| edge | source in the plan |
| --- | --- |
| reference | `configuration.root_module.resources[].expressions[].references` |
| IAM grant | policy documents in `planned_values`, matched by action service prefix and ARN pattern |
| network | security-group ingress rules, with `0.0.0.0/0` originating from a synthetic `internet` node |
| assume | `iam_instance_profile` → instance profile → role |

Reach is computed twice — once over `prior_state`, once over `planned_values` — and the findings
are the difference. A path that already existed is reported **only** if this plan made it broader.

Severity, first rule that matches:

- **critical** — wildcard in an IAM `Action` or `Resource`
- **critical** — new ingress from `0.0.0.0/0` or `::/0`
- **high** — a new path to a data store (S3, RDS, DynamoDB, EBS, Secrets Manager, SSM, EFS)
- **low** — any other newly added reach

## What it does not evaluate

Stated in the UI as well as here, because the limits decide whether the output is trustworthy:

- **Reach is as asserted by the policy documents in the plan.** IAM conditions, permission
  boundaries, SCPs and explicit denies are not evaluated. This is not an effective-permissions
  engine.
- **Root module only.** Child modules and `for_each` / `count` expansion are not followed.
- **ARN matching is pattern-based** (`*`, `prefix/*`, exact), not full IAM wildcard semantics.
- **No AWS API access.** Nothing is resolved against a real account, so `known after apply`
  values stay unknown rather than being guessed.

## About the example plan

`demo/plan.json` is genuine `terraform show -json` output from Terraform 1.13.1 against
`demo/main.tf`.

`demo/terraform.tfstate` is a **synthetic baseline state**, generated by `demo/seed_state.py`.
It is well-formed but no AWS account was ever contacted: the plan is produced with
`terraform plan -refresh=false`, which makes zero API calls and applies nothing. Account IDs in
the fixtures are the AWS-reserved documentation ID `111122223333`. The baseline represents a
world a team already reviewed and accepted (a narrow `s3:GetObject` policy, office-only SG
ingress); the plan under review then adds `s3:*` on `*` and opens the SG to the internet.

Regenerate it with:

```sh
cd demo
python3 seed_state.py
terraform init
terraform plan -refresh=false -out=tfplan
terraform show -json tfplan > plan.json
```
